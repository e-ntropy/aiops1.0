# 第三条简历：Hybrid RAG 面试题 30 题

> 回答口径：指标来自仓库历史报告；因果结论只说到实验实际隔离的变量。每题建议先讲结论，再讲链路、证据和边界。

## Q01：为什么运维知识库比普通 FAQ 更难召回？

### 难度
基础

### 面试问题
运维文档检索的主要困难是什么？

### 面试官考察点
能否从数据形态而非模型名解释问题。

### 推荐回答
运维文档通常标题层级深、命令和错误码密集，同一故障还会跨“现象—原因—处置”多个段落。查询往往很短，但答案需要较完整上下文。固定小块有利于命中关键词，却容易截断步骤；大块语义完整，却会稀释 embedding。因此项目用 Child 做精确召回、Parent 做生成上下文，并用 BM25 补错误码和专有词召回。

### 代码证据
`app/core/splitter.py::split_markdown()`；`app/rag/retrieval.py::build_context()`。

### 面试官可能继续追问
1. 哪类查询更依赖 BM25？  
2. 哪类查询更依赖向量召回？

### 追问简答
错误码、命令、指标名偏 BM25；同义表达、自然语言现象偏 dense。实际应按查询集分桶验证，而不是凭直觉固定权重。

### 我需要掌握的知识
领域语料特征、词法检索、语义检索、上下文完整性。

## Q02：Parent-Child 分块的核心原则是什么？

### 难度
基础

### 面试问题
为什么不直接把检索到的小块交给模型？

### 面试官考察点
召回粒度与生成粒度的分离。

### 推荐回答
Child 的职责是提高定位精度，Parent 的职责是恢复语义和操作步骤的完整性。检索阶段用较短 Child 降低主题混杂，生成阶段按 `parent_id` 去重并使用 `parent_content`。这解决的是“容易找到”和“足够回答”两个目标冲突，不等于 Parent 一定越大越好，父块仍受最大字符数和上下文预算约束。

### 代码证据
`split_markdown()` 写入 `parent_id`、`parent_content`；`build_context()` 回填父块。

### 面试官可能继续追问
1. Parent 太大会怎样？  
2. 多个 Child 命中同一 Parent 怎么办？

### 追问简答
Parent 太大会引入噪声和 token 成本；当前实现按 `parent_id` 去重，只保留一次父内容。

### 我需要掌握的知识
Small-to-big retrieval、上下文预算、去重。

## Q03：Child 和 Parent 在项目里分别怎样存储？

### 难度
中等

### 面试问题
这个项目是否有独立的 Parent 表或 Parent collection？

### 面试官考察点
是否真正读过存储实现。

### 推荐回答
没有独立 Parent 表。Milvus 中写入的是 Child Document，每个 Child 的 metadata 冗余保存 `parent_id` 和 `parent_content`。回溯时不是再查一次父库，而是从命中 Child 的 metadata 取父内容。优点是链路简单、少一次查询；缺点是父内容重复存储，更新一致性和存储放大会更明显。

### 代码证据
`app/core/splitter.py` 的 Child metadata；`app/rag/retrieval.py` 读取 `parent_content`。

### 面试官可能继续追问
1. 这种冗余的成本是什么？  
2. 生产化会怎样改？

### 追问简答
成本是重复数据、更新扇出和索引体积；可拆成 Child 向量表加 Parent 文档表，以稳定 ID 关联并做版本控制。

### 我需要掌握的知识
反范式化、读写放大、数据一致性。

## Q04：Parent ID 和 Chunk ID 如何设计？

### 难度
中等

### 面试问题
怎样保证重新摄取后父子关系可追踪？

### 面试官考察点
稳定标识、幂等摄取和版本化。

### 推荐回答
当前 `_parent_id` 根据来源和父内容生成稳定哈希，Child 通过 metadata 引用它，并记录 `chunk_index`；Milvus 主键 `pk` 使用自动 ID。稳定 Parent ID 便于同内容去重，但内容改变会产生新 ID。要支持可控更新，我会增加 `document_id/version/chunk_id`，把内容哈希作为校验而不是唯一业务身份。

### 代码证据
`app/core/splitter.py::_parent_id()`；`app/core/vector_store.py` 的 `auto_id` 与 `pk`。

### 面试官可能继续追问
1. 为什么不能只用 Python `hash()`？  
2. 内容哈希 ID 有什么问题？

### 追问简答
Python hash 跨进程可能变化；内容哈希在内容微调时身份漂移，不利于增量更新和引用稳定。

### 我需要掌握的知识
稳定哈希、业务 ID、内容寻址、幂等。

## Q05：为什么用 Child 召回？

### 难度
基础

### 面试问题
Child 召回相较整篇或 Parent 召回有什么优势？

### 面试官考察点
检索精度与语义稀释。

### 推荐回答
短块主题更集中，错误码、命令或故障现象在向量中不容易被同篇其他内容稀释，也更适合 BM25 排名。项目会先 over-fetch Child，再按 Parent 去重构建上下文。但块太短会失去必要语义，因此必须和 overlap、标题 metadata、Parent 回填共同设计。

### 代码证据
`build_context()` 以目标数量约三倍 over-fetch Child；`split_markdown()` 保留 chapter/source。

### 面试官可能继续追问
1. over-fetch 为什么必要？  
2. Child 越短越好吗？

### 追问简答
多个 Child 可能映射同一 Parent，去重后数量会下降；太短会导致语义残缺和大量近重复块。

### 我需要掌握的知识
召回率、去重损耗、语义密度。

## Q06：为什么生成阶段使用 Parent？

### 难度
基础

### 面试问题
父块回填具体改善什么？

### 面试官考察点
答案完整性和可解释性。

### 推荐回答
运维回答常需要前置条件、连续步骤和风险提示，小块可能只命中某一条命令。父块回填能把命中点周边的完整章节交给模型，减少断章取义。代价是噪声与 token 增加，所以当前实现还做 Parent 去重和总长度截断。

### 代码证据
`app/rag/retrieval.py::build_context()` 的 Parent 去重、回填与 `max_chars` 截断。

### 面试官可能继续追问
1. 为什么不回填整篇文档？  
2. 父块截断会不会再次破坏步骤？

### 追问简答
整篇通常噪声和成本过高；字符级截断确有风险，改进方向是按标题/段落边界压缩。

### 我需要掌握的知识
上下文构造、结构化截断、答案完整性。

## Q07：Chunk size 和 overlap 怎么选？

### 难度
中等

### 面试问题
项目参数是多少，又如何证明合理？

### 面试官考察点
参数意识和实验方法。

### 推荐回答
代码配置默认 Child 约 300 字符、overlap 50、Parent 最大 2400，但环境配置可覆盖，所以面试中不把它说成唯一线上值。选参要按标题结构、token 分布和检索集做网格实验，观察 Hit/MRR、重复率、Parent 覆盖与生成 token，而不是只优化一个召回指标。

### 代码证据
`app/config.py` 的 `rag_chunk_size`、`rag_chunk_overlap`、`rag_parent_max_chars`；`.env.example` 可覆盖。

### 面试官可能继续追问
1. overlap 太大会怎样？  
2. 为什么字符数不如 token 精确？

### 追问简答
会扩大索引、制造近重复命中；不同语言和代码的字符/token 比例不同，token-aware splitter 更可控。

### 我需要掌握的知识
分块实验、tokenization、近重复。

## Q08：Overlap 解决什么问题？

### 难度
基础

### 面试问题
为什么相邻 Child 要重叠？

### 面试官考察点
边界效应。

### 推荐回答
Overlap 缓解关键实体、条件和结论恰好被切分边界拆开的情况，让相邻块都保留局部上下文。但它不是免费的，会增加存储、embedding 成本和重复召回，所以需要结合 Parent 去重并通过实验选择。

### 代码证据
`split_markdown()` 使用配置的 chunk overlap；`build_context()` 做父级去重。

### 面试官可能继续追问
1. 标题感知切分能否替代 overlap？  
2. 如何测重复率？

### 追问简答
不能完全替代，长章节内仍需切分；可统计相邻块相似度、命中 Parent 的唯一率和索引膨胀比。

### 我需要掌握的知识
边界效应、冗余率、结构化分块。

## Q09：Milvus schema 和索引如何设计？

### 难度
中等

### 面试问题
项目里的向量 collection 有哪些关键配置？

### 面试官考察点
向量库工程细节。

### 推荐回答
LangChain Milvus 配置使用 `pk` 主键、`content` 文本字段和 `vector` 向量字段，主键自动生成；索引是 HNSW，距离为 COSINE，参数包含 `M=8`、`efConstruction=64`，查询 `ef` 来自配置。metadata 承载 source、chapter、parent 关联等信息。参数只是当前实现，容量和延迟变化后仍需压测。

### 代码证据
`app/core/vector_store.py::get_vector_store()`。

### 面试官可能继续追问
1. HNSW 的 M 与 ef 有何权衡？  
2. COSINE 要注意什么？

### 追问简答
更大参数通常提高召回但增加内存、建索引或查询成本；需确认 embedding 的归一化与距离语义一致。

### 我需要掌握的知识
ANN、HNSW、距离度量、schema。

## Q10：Embedding 层如何影响检索？

### 难度
中等

### 面试问题
替换 embedding 模型需要做什么？

### 面试官考察点
模型、维度、索引版本的一致性。

### 推荐回答
Embedding 决定语义空间，替换模型不仅是改配置，还可能改变维度、归一化和领域适配，旧向量不能直接混用。应新建带版本的 collection，重做 corpus embedding，跑同一检索集和生成评估，再灰度切换。项目通过 provider/config 封装模型，但完整索引版本治理仍是改进项。

### 代码证据
`app/core/embedding.py::get_embeddings()`；`app/config.py` embedding 配置。

### 面试官可能继续追问
1. 查询和文档能否用不同模型？  
2. 维度一致就能混用吗？

### 追问简答
除非模型明确按双塔配套训练，否则不应混用；维度相同也不代表语义空间相同。

### 我需要掌握的知识
向量空间、模型版本、重建索引。

## Q11：项目中的 BM25 索引是怎样构建的？

### 难度
中等

### 面试问题
BM25 是 Milvus 原生能力还是独立服务？

### 面试官考察点
实现边界和扩展性。

### 推荐回答
当前是进程内 `_BM25Index`，启动或刷新时从 Milvus 拉取全部 Child，再在内存建立词法索引；不是独立 Elasticsearch，也不是 Milvus 服务端 BM25。实现简单，适合参考项目和小规模语料，但全量加载上限、每进程副本和更新新鲜度会限制规模化。

### 代码证据
`app/core/hybrid_retriever.py::_BM25Index`、`_load_all_chunks_from_milvus()`，加载上限 16384。

### 面试官可能继续追问
1. 多 worker 会发生什么？  
2. 增量更新怎么做？

### 追问简答
每进程可能持有自己的副本并出现版本差；可用服务端 sparse index 或集中检索服务，并用版本/事件触发刷新。

### 我需要掌握的知识
BM25、内存索引、多进程一致性。

## Q12：Dense retrieval 的调用链是什么？

### 难度
基础

### 面试问题
从 query 到候选文档经过哪些函数？

### 面试官考察点
源码追踪能力。

### 推荐回答
入口 `build_context()` 调用 `advanced_search()`；后者先通过 Milvus similarity search 取 dense 候选，在 hybrid 开启时再取 BM25 候选并融合，之后可选 rerank。异常时会按层降级。最后 `build_context()` 做 Parent 去重和上下文拼装。

### 代码证据
`app/rag/retrieval.py::build_context()`；`app/core/vector_store.py::advanced_search()`。

### 面试官可能继续追问
1. `retrieve_k` 和最终 k 为什么不同？  
2. rerank 在哪一层？

### 追问简答
粗排需扩大候选池，给融合、去重和 rerank 留空间；rerank 位于融合候选之后、Parent 上下文构造之前。

### 我需要掌握的知识
多阶段检索、粗排、精排。

## Q13：候选结果如何去重？

### 难度
中等

### 面试问题
Dense 与 BM25 命中同一块、多个 Child 命中同一父块时分别怎么办？

### 面试官考察点
不同层级的去重键。

### 推荐回答
融合阶段需要把两路同一 Child 视为同一候选，RRF 累加其排名贡献；上下文阶段再按 `parent_id` 去重，避免同一父章节重复进入 prompt。旧索引缺少 Parent metadata 时，代码用内容哈希兼容回退。要注意当前 Hybrid 实现使用 Python `hash(page_content)` 作为候选键，跨进程稳定性不足。

### 代码证据
`hybrid_retriever.py::hybrid_search()`；`rag/retrieval.py::build_context()`。

### 面试官可能继续追问
1. 为什么应使用稳定 chunk_id？  
2. 内容相同但来源不同怎么处理？

### 追问简答
稳定 ID 支持跨进程、缓存和审计；是否合并同内容异来源要按引用与权限需求决定，通常保留来源身份。

### 我需要掌握的知识
实体身份、候选融合、父级去重。

## Q14：RRF 的公式是什么，项目做了什么变体？

### 难度
中等

### 面试问题
请解释当前融合打分。

### 面试官考察点
是否能准确说公式。

### 推荐回答
标准思想是每个列表按名次贡献 `1/(k+rank)`，不直接比较异构原始分数。项目代码对每一路加权，形式为 `weight/(rrf_k + rank + 1)`，同一候选累加 dense 和 BM25 贡献，再按总分排序。因此严格说是 weighted RRF。

### 代码证据
`app/core/hybrid_retriever.py::hybrid_search()`。

### 面试官可能继续追问
1. 为什么代码有 `+1`？  
2. 权重如何选？

### 追问简答
rank 使用零基计数，`+1` 转为第一名；权重应在验证集上按查询类型或全局网格搜索。

### 我需要掌握的知识
RRF、rank fusion、零基排名。

## Q15：RRF 的 rank constant 有什么作用？

### 难度
中等

### 面试问题
`rrf_k=60` 改大或改小会怎样？

### 面试官考察点
参数直觉与验证意识。

### 推荐回答
常数越小，头部名次差异越突出；越大，各名次贡献更平滑，两路共同出现的候选相对更占优势。历史报告使用 60，但这只是一次实验配置，不是普适最优。应结合候选深度和数据集做敏感性分析，并报告均值与波动。

### 代码证据
历史报告 `retrieval_20260728-132213.json` 的 `rrf_k=60`；融合公式见 `hybrid_retriever.py`。

### 面试官可能继续追问
1. 常数与 top-N 有什么关系？  
2. 能否在线动态调整？

### 追问简答
候选越深，尾部贡献控制越重要；可以按查询分类调参，但要防止规则过拟合并保留统一离线回归集。

### 我需要掌握的知识
超参数敏感性、候选深度、过拟合。

## Q16：为什么选择 RRF，而不是直接加权原始分数？

### 难度
中等

### 面试问题
BM25 与 cosine score 为什么不直接相加？

### 面试官考察点
异构分数校准。

### 推荐回答
BM25 分数和 cosine 相似度的范围、分布与查询相关性不同，直接相加前必须校准，否则权重没有稳定含义。RRF 只依赖排序，对尺度差异更鲁棒，实现也简单。代价是丢失同一路候选之间的分数间隔；数据成熟后可尝试归一化、学习排序或 learned fusion。

### 代码证据
`hybrid_retriever.py::hybrid_search()` 只使用 rank 和配置权重。

### 面试官可能继续追问
1. RRF 会丢掉什么信息？  
2. 何时值得学习融合？

### 追问简答
丢掉原始置信度间隔；有足量、有代表性的标注和稳定线上反馈时才值得训练融合模型。

### 我需要掌握的知识
分数校准、rank fusion、learning to rank。

## Q17：Hit@3 如何计算？

### 难度
基础

### 面试问题
本项目的 Hit@3 是文档命中还是答案命中？

### 面试官考察点
指标定义准确性。

### 推荐回答
它是检索指标：对每个 query，看 top 3 结果是否覆盖至少一个 gold 关键词组，命中记 1，否则 0，再对样本平均。Gold 组内是 OR 匹配，不是 LLM 判断答案正确，因此不能等价于端到端回答成功率。

### 代码证据
`benchmark/run_benchmark.py::score_hits()`；`benchmark/retrieval_rk_50.jsonl`。

### 面试官可能继续追问
1. 关键词匹配有什么偏差？  
2. Hit@3 为 1 代表什么？

### 追问简答
会受同义词和偶然包含影响；只代表前三条至少有相关证据，不代表排序第一或生成可靠。

### 我需要掌握的知识
Hit@K、gold 标注、代理指标。

## Q18：MRR@3 如何计算？

### 难度
基础

### 面试问题
为什么已有 Hit@3 还需要 MRR@3？

### 面试官考察点
首个相关结果的位置敏感性。

### 推荐回答
MRR@3 取首个命中结果的倒数排名：第 1 名是 1，第 2 名是 1/2，第 3 名是 1/3，前三无命中是 0，再求平均。它比 Hit@3 更关注正确证据是否排在前面，适合上下文预算有限的 RAG。

### 代码证据
`benchmark/run_benchmark.py::score_hits()` 中首次命中后设置 reciprocal rank。

### 面试官可能继续追问
1. 多个相关文档时 MRR 的局限？  
2. 可补什么指标？

### 追问简答
MRR 只看第一个相关结果，忽略后续覆盖；可补 Recall@K、nDCG 和分组覆盖率。

### 我需要掌握的知识
MRR、排名指标、nDCG。

## Q30：下一步会怎样改进 RAG？

### 难度
高级

### 面试问题

### 面试官考察点

### 推荐回答

先修评测与失败样本，因为它决定后续投入；保留原 query，多路检索，并对实体、错误码和约束做一致性检查。
