# 第四条简历：设计解释

## 为什么 Postgres + Redis

Postgres 保存可审计的事实和最终状态，Redis Streams 承担低延迟排队、Consumer Group 分工、PEL 与超时认领。两者职责分离，但也引入跨系统一致性问题；当前实现是“先落事实、再投消息”和基于任务状态的恢复思路，尚未达到事务 Outbox 级保证。

## 为什么采用 at-least-once

消息只有在处理成功、事实状态提交后才 ACK。Worker 崩溃会使消息留在 PEL，之后由 `XAUTOCLAIM` 重新认领，因此更倾向“不丢任务”，代价是允许重复执行。项目通过成功状态短路减少重复，但外部副作用仍需要独立幂等键。

## 四层评测各回答什么问题

1. Router：Skill 选择与 OOS 拒识是否正确。
2. Retrieval：证据是否能在 top-k 被找到并排到前面。
3. RAGAS：回答忠实性、相关性与上下文质量。
4. Diagnosis E2E：完整图能否跑通，以及 RCA 排名等任务指标。

分层的价值是定位故障层；各层样本相加可以描述评测资产规模，不能混成统一成功率。
