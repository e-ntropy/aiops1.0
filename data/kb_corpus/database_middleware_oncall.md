# 数据库与缓存中间件只读 Runbook

## 证据链原则

数据库事故不能只凭应用报错定根因。最小证据链应同时覆盖用户影响、应用连接池、数据库或缓存指标，以及同一时间窗内的直接状态。知识库内容是排查方法，不是现场证据。

## MySQL 锁等待

1. 记录故障时间窗、实例和受影响接口。
2. 比较活跃连接、threads_running、锁等待数量、事务时长和查询延迟趋势。
3. 将等待事务与阻塞事务区分开；被阻塞的慢 SQL 通常不是根因。
4. 检查长事务开始时间是否与发布、批任务或流量变化一致。
5. 在没有事务快照时，只能给“锁竞争候选”，不能宣称已定位具体 SQL。

## Redis 连接与内存

1. 对齐 connected_clients、rejected_connections、maxclients、used_memory、evicted_keys 和命中率。
2. 应用连接池 timeout 可能由 maxclients、网络抖动、服务端延迟或客户端连接泄漏造成。
3. `OOM command not allowed` 需要日志/错误计数与内存策略同时佐证；高内存单点不能证明持续 OOM。
4. 处置动作如调整 maxclients、淘汰策略、重启或清理 Key 必须人工审批，本平台只给建议。

## 失败关闭

若监控、日志和直接状态均不可用，应输出数据源失败与补数清单，不生成确定根因。若证据冲突，应保留反证并升级深度诊断。
